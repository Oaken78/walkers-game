## Goal
The walker's build as pure data: a part catalog that mirrors the GDD 8.1 table, and a `WalkerBuild` that holds
which part sits in which socket, computes every derived stat from that part list, and says why a build is invalid.
No nodes, no scenes. Every later system reads builds through this: T03 (legs, speed, step-up, slope), T06 (cannon
numbers and spread), T09 (place, remove, stat deltas, the blocked-exit reason), T12. When done, code can build the
Scout, Strider and Crawler, swap parts, read their stats, and get the exact reason string the workshop shows.

## Contract (other packets code against these names; do not rename)

### `PartCatalog` (`class_name PartCatalog extends RefCounted`, static functions only)
Part ids are `StringName` consts: `CHASSIS_MEDIUM = &"chassis_medium"`, `LEG_SHORT = &"leg_short"`,
`LEG_MEDIUM = &"leg_medium"`, `LEG_LONG = &"leg_long"`, `PULSE_CANNON = &"pulse_cannon"`,
`ARMOR_PLATE = &"armor_plate"`.

One const table at the top of the file, one row per part, values exactly as below (GDD 8.1 and section 5). It is
the only place these numbers live; logic never repeats them.

| id | socket | mass | lift | reach | slope_grip | spread_factor | hp | fire_rate | damage | projectile_speed | price | units_per_purchase | for_sale |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| chassis_medium | chassis | 125 | 0 | 0 | 0 | 0 | 100 | 0 | 0 | 0 | 0 | 1 | false |
| leg_short | leg | 35 | 110 | 0.6 | 45 | 0.5 | 0 | 0 | 0 | 0 | 40 | 2 | true |
| leg_medium | leg | 25 | 75 | 1.0 | 35 | 1.0 | 0 | 0 | 0 | 0 | 0 | 2 | false |
| leg_long | leg | 20 | 85 | 1.6 | 30 | 1.5 | 0 | 0 | 0 | 0 | 70 | 2 | true |
| pulse_cannon | top | 40 | 0 | 0 | 0 | 0 | 0 | 4.0 | 15 | 60.0 | 80 | 1 | true |
| armor_plate | top | 50 | 0 | 0 | 0 | 0 | 40 | 0 | 0 | 0 | 50 | 1 | true |

- `price` is per purchase; `units_per_purchase` is 2 for legs because M0 sells them in mirrored pairs (M1 sells
  singly at half price: a data change). Medium legs are starting parts and not for sale in M0 (GDD price "start").
- `hp` is the chassis base HP, or the bonus an armor plate adds.
- Rows also carry a `display_name` (`"Short leg"`, `"Pulse cannon"`, ...) for the workshop list.

Functions:
- `has_part(id: StringName) -> bool`
- `get_part(id: StringName) -> Dictionary` (a copy of the row; empty Dictionary for an unknown id)
- `part_ids() -> Array[StringName]`
- `socket_kind(part_id: StringName) -> StringName` (`&"leg"`, `&"top"`, `&"chassis"`, or `&""` if unknown)
- `chassis_sockets(chassis_id: StringName) -> Array[Dictionary]`, each `{id, kind, side, row}`:
  `leg_l0`..`leg_l3` (kind `&"leg"`, side -1, rows 0-3), `leg_r0`..`leg_r3` (side +1, rows 0-3),
  `top_0`..`top_2` (kind `&"top"`, side 0, rows 0-2). Side -1 is the walker's left (-X in its local space; Godot
  forward is -Z), +1 its right. Row 0 is the front. Rows are an order, not positions: T03 decides where sockets
  sit on the body.
- `starting_inventory() -> Dictionary` = `{chassis_medium: 1, leg_medium: 6, pulse_cannon: 1}` (GDD 8.1).

### `WalkerBuild` (`class_name WalkerBuild extends RefCounted`)
- `var chassis_id: StringName`; `_init(chassis: StringName = PartCatalog.CHASSIS_MEDIUM)`.
- `static func scout() -> WalkerBuild`, `strider()`, `crawler()`: the fixtures below.
- `copy() -> WalkerBuild`: an independent copy (T09 previews deltas on a copy).
- `can_place(socket_id, part_id) -> bool`; `place(socket_id, part_id) -> bool`: false, and no change, when the
  socket or part is unknown, the part's kind does not match the socket's kind, or the socket is occupied (the
  caller removes first, so inventory accounting stays explicit).
- `remove(socket_id) -> StringName`: the removed part id, or `&""` if the socket was empty or unknown.
- `part_at(socket_id) -> StringName` (`&""` when empty); `parts() -> Dictionary` (a copy, socket id -> part id).
- `leg_count() -> int`.
- `mounted_legs() -> Array[Dictionary]`: one entry per mounted leg, `{socket, part, side, row, mass, lift, reach,
  slope_grip, spread_factor}`, ordered left side front to back, then right side front to back. This is the per-leg
  data T03 builds the rig from; nothing in it assumes pairs.
- `stats() -> Dictionary` with exactly these keys, computed on every call from the part list (no cached state):

| Key | Formula (GDD 8.1) |
|---|---|
| `mass` | chassis mass + sum of part masses |
| `lift` | sum of leg lift |
| `load` | mass / lift |
| `reach` | mean leg reach |
| `top_speed` | clamp(4.5 x sqrt(reach) x gait_factor x (1.7 - load), 2.5, 7.0); gait_factor 0.85 for 4 legs, else 1.0 |
| `turn_rate` | clamp(250 - 100 x load - 10 x legs, 60, 180) |
| `step_up` | 0.6 x reach |
| `max_slope` | lowest slope_grip among mounted legs |
| `spread` | 1.0 deg x mean leg spread_factor (this is the cannon's cone; T06 reads it here) |
| `hp` | chassis hp + sum of armor hp |
| `dps` | sum over weapons of fire_rate x damage |
| `leg_count` | number of mounted legs |

  Every number in the formulas (4.5, 1.7, 0.85, 2.5, 7.0, 250, 100, 10, 60, 180, 0.6, 1.0) is a named const in
  `walker_build.gd`, not a literal in the logic. A build with no legs returns finite values: `lift`, `load`,
  `reach`, `top_speed`, `turn_rate`, `step_up`, `max_slope` and `spread` are 0 (no division by zero, no NaN, no INF).
- `is_valid() -> bool` and `invalid_reason() -> String`. Rules are checked in this order and the first failure wins
  (leg count first because it is the fix the player makes first):
  1. leg count not 4, 6 or 8: `"Needs 4, 6 or 8 legs"`
  2. left count != right count: `"Legs unbalanced"`
  3. mass > lift: `"Overloaded: %d/%d kg" % [roundi(mass), roundi(lift)]`, e.g. `"Overloaded: 345/300 kg"`

  A valid build returns `""`. An invalid build is a normal state (the workshop allows it and blocks exit), so
  never `push_error` for it or for bad ids; return false or empty values.

### Fixtures and expected values (lead pre-computed from the formulas)
Scout and Strider put legs on `leg_l0`-`leg_l2` and `leg_r0`-`leg_r2` and the cannon on `top_0`. Crawler fills all
8 leg sockets with short legs, cannons on `top_0` and `top_1`, armor on `top_2`. The GDD table rounds turn rate to
whole degrees; assert these values within 0.01:

| Build | mass | lift | load | reach | top_speed | turn_rate | step_up | max_slope | spread | hp | dps |
|---|---|---|---|---|---|---|---|---|---|---|---|
| Scout | 315 | 450 | 0.700 | 1.0 | 4.500 | 120.000 | 0.60 | 35 | 1.0 | 100 | 60 |
| Strider (A) | 285 | 510 | 0.559 | 1.6 | 6.496 | 134.118 | 0.96 | 30 | 1.5 | 100 | 60 |
| Crawler (B) | 535 | 880 | 0.608 | 0.6 | 3.807 | 109.205 | 0.36 | 45 | 0.5 | 140 | 120 |

Contrast (A - B) / A: top speed 41.4 %, step-up 62.5 %. DPS x HP: B / A = 2.8.

Clamp check: every valid build with at least one cannon and 6 or 8 legs (any mix of leg types, any top parts) has
an unclamped top speed between 3.417 and 6.956 m/s, so it never touches the clamp (GDD: "no armed build of 6+ legs
may reach it"). 4-leg armed builds can go below 2.5 (4 short legs, cannon, 2 armor = 2.31) and are clamped; that
is allowed. If a test disagrees with these numbers, the code is wrong or the GDD is: stop and report, do not tune
numbers to pass.

## Out of scope
- Inventory, buying and scrap (T08, T09). Placing a mirrored pair is workshop UX (T09 calls `place` twice).
- Socket positions on the body, the leg rig, and anything that moves (T03).
- The weapon node, projectiles and the turret arc (T06 reads fire_rate, damage and projectile_speed from
  `PartCatalog` and its cone from `stats().spread`).
- M1 uneven-build rules (imbalance penalty, 2 legs per side minimum). Keep the per-leg data so they stay a rules
  change.
- Moving the catalog to `.tres` Resources: a const table is enough for 6 parts.
